You are a senior Python platform engineer and distributed systems architect. Investigate an enterprise agent execution platform running on OpenShift/Kubernetes.

Do not immediately modify code. First inspect the entire implementation and produce an evidence-based diagnosis. Then propose fixes in priority order, and only after that suggest exact code changes.

## System Context

* API service receives or creates a run/request.
* Request is sent through Kafka.
* An executor running in OpenShift/OCP consumes the Kafka request.
* The executor uses the request/run configuration to process work items stored in a database.
* A run may contain anywhere from 1 work item to a very large number of work items.
* Executor repeatedly claims work items from the database.
* Work item statuses: NEW, PENDING, CLAIMED, IN_PROGRESS, SUCCESS, FAILED, RETRY.
* Agents are implemented using Google ADK or an ADK-based agent framework.
* Executor supports parallel processing with a configurable maximum of approximately 5 threads/workers.
* Each worker/agent claims a record from the database, executes the configured flow, and updates the database.
* Executor continues checking for NEW, PENDING, FAILED, RETRY, or recoverable items until no work remains.
* Result-processing logic traverses the ADK/agent output to determine: success, failure, in-progress, error details, error message, final output.
* Once all work items for the run are completed, the executor updates run completion status in the database and publishes completion/status information back through Kafka.

## Primary Problem

Memory usage in the executor pod keeps increasing and is not released — even when parallel execution is disabled, thread max is small (~5), and a run finishes successfully. Pod RSS/memory reported by OpenShift remains high or continues increasing between work items or between runs.

We need to determine whether this is:

1. a real Python object/reference leak
2. ADK session/event/history retention
3. agent output/result retention
4. thread/future retention
5. database connection/session leakage
6. HTTP/client/tool connection leakage
7. logging/tracing/telemetry buffering
8. cache growth
9. asyncio task retention
10. Python garbage collection behavior
11. CPython/glibc allocator fragmentation/high-water-mark behavior
12. third-party library native-memory retention
13. deployment/runtime configuration (including cgroup memory accounting artifacts)
14. a combination of the above

# PHASE 7 — Database Connection and Session Investigation

Identify DB technology (SQLAlchemy, psycopg, pyodbc, asyncpg, SQL Server, PostgreSQL, Oracle, other).

Inspect engine creation, session factory, session lifecycle, connection pool, cursor/transaction/result-set lifecycle. Verify `session.close()`, `connection.close()`, `cursor.close()`, rollback on exception, and context-manager usage.

# PHASE 13 — malloc_trim Diagnostic (lower environment only)

​```python
import ctypes, gc
gc.collect()
libc = ctypes.CDLL("libc.so.6")
libc.malloc_trim(0)
​```

Measure RSS before GC, after GC, after `malloc_trim`.

* Large drop after `malloc_trim` (e.g. 1800→1750→800 MB) → allocator fragmentation/high-water-mark, not a live-object leak.
* Small drop throughout (e.g. 1800→1780→1750 MB) → live objects/references are likely still held.

Do not deploy `malloc_trim` to production blindly — diagnostic only at this stage.

# PHASE 27 — Acceptance Criteria

For sequential execution of 100+ comparable work items: memory rises during warm-up, then plateaus; it does not grow roughly linearly per item; ADK session count and event/history object count do not grow indefinitely; completed futures/tasks are released; DB and HTTP connections remain bounded; run-level objects disappear after run completion.

For multiple consecutive runs in the same pod: memory after completion stays within an explainable bounded range instead of continuously increasing across Run 1 → Run 5.

For parallel execution at MAX_WORKERS=5: no duplicate claims, no stranded work items, correct status updates, no runaway thread/task count, memory remains bounded.

# IMPORTANT INVESTIGATION RULES

1. Do not assume high RSS automatically means a Python memory leak — check cgroup accounting and page cache first.
2. Distinguish live-object retention from allocator-retained memory (malloc_trim test).
3. Do not solve this only by increasing OCP memory limits.
4. Do not add `gc.collect()` everywhere without understanding ownership.
5. Do not blindly restart pods as the only fix.
6. Do not rewrite the entire architecture before identifying root cause.
7. Do not change business behavior.
8. Do not change Kafka semantics unless required.
9. Preserve existing run/work-item status behavior unless it is incorrect.
10. Preserve maximum concurrency configuration.
11. Focus first on sequential execution — the issue occurs there too.
12. Use evidence from the repository, runtime instrumentation, and deployment configuration.
13. Explicitly identify which findings are confirmed versus inferred.
14. When you find an issue, point to the exact file/class/function/code path.
15. After fixing each issue, rerun the controlled memory tests.

The primary goal: find exactly why memory stays allocated or grows after an ADK work item and after a complete run, fix the real ownership/lifecycle problem, and prove the OCP executor can operate as a stable long-running service.
